# 批量操作不做部分生效：用户类整批拒绝，删除类按幂等

管理后台的列表需要批量操作。常识默认是「批量 = 逐个调用单条接口」，本文记录为什么这里**刻意不走**这条默认路径，以及为什么用户类与删除类用了两套不同的失败语义。

## 接口形态：一个请求处理一整批

单条接口的规则里有一条天然的跨条目约束——「不能停用或删除当前登录账号」「至少保留一名可登录管理员」。前端循环调单条时，每条请求各自读一次库，判定退化成逐条：

> 库中有 2 名可登录管理员 A、B，一次勾选 A、B 停用。
> 逐条判：处理 A 时看到「还有 B 可登录」→ 放行；处理 B 时看到「还有 A」→ 放行。
> 结果两名管理员全被停用，后台无人可进。

把一批放进同一个请求，服务层才能拿**整批消耗掉的名额**去减：「当前 2 名 − 本批命中 2 名 = 0」→ 拒绝。这是批量接口存在的根本理由，不是为了省请求数。

## 失败语义：两类分开

| 类别                      | 语义                                             | 理由                                                                                          |
| ------------------------- | ------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| 用户（停用 / 启用、删除） | **整批拒绝**：先整体预检，任一项命中规则就不执行 | 规则本身是硬约束；若部分生效，用户看到的「成功 N 条」里混着被静默跳过的项，无法解释也无法信任 |
| 文档 / 文件 / 会话的删除  | **幂等**：不存在视为已完成，逐条删到底           | 没有业务规则约束，批量删除的意图就是「这些都不该再存在」，中途失败重试即可收敛                |

「整批拒绝」不等于事务回滚：用户类的预检都在写操作之前完成，预检通过后才是逐条执行；删除类更是**刻意不引入跨 Store 事务**——文档的向量片段在 LanceDB、元数据在 MySQL，账号删除还要跨会话 / 对话 / 文件三张表，为一个可重试的操作铺事务，成本远大于收益。账号删除本就走「先删从属再删账号」，中途失败时账号仍在，重试不会有害（已清理的部分重复删除不报错）。

## 入参口径

`ids` 去重后不能为空；含非法项（非正整数、空串、非字符串）一律 `400`，不猜测意图。用户类只认 JSON 数字，不做 `Number()` 强转——`Number(true)` 得 1、`Number(['2'])` 得 2，强转等于替调用方猜意图。用户类接口在目标已消失时回 `404`，提示刷新后重试——批量语境下泛化的「用户不存在」说不清是哪一条。

## 前端选择态的生命周期

选中集合不做跨页保留：翻页、搜索、重新加载后一律清空，表头复选框只作用于当前页。理由是「选中全部匹配项」需要一个当前接口给不出的「全部匹配」id 集合，硬做就得让服务端额外回一份 id 列表；而管理端批量操作的典型用法是「在眼前这一页里挑几条处理」，跨页保留带来的「看不见却还选着」的误删风险更不值得接受。

## Considered Options

- **前端循环调单条接口**：否决。跨条目判定无法表达（见上），且失败语义会碎成 N 份。
- **用户类也按幂等处理（跳过不可操作项，其余照删）**：否决。勾到自己却被静默跳过时，用户会以为「删除成功」里包含自己，或反过来不理解为何数量对不上。
- **为批量删除引入跨 Store 事务**：否决。MySQL 与 LanceDB 两套存储，事务要跨两套，收益仅是「少一次重试」。
- **新增「选中全部匹配项」**：不做。需要服务端额外回一份 id 集合，超出本仓库当前列表接口的形状。

## Consequences

- 用户类接口有两个：`POST /api/admin/users/batch-status`（`200 { updated }`）与 `POST /api/admin/users/batch-delete`（`204`）；文档 / 文件 / 会话各一个 `*/batch-delete`（`204`）。接口表见 [apps/agent-server/README.md](../../apps/agent-server/README.md)。
- 名额判定必须按整批算，`services/adminUsers.ts` 的 `consumedAdminSlots` 因此接收整批目标而不是单个；单条接口保留原有 `isLastActiveAdmin`，两者语义一致（整批大小为 1 时等价）。
- `ids` 的解析收在 `routes/admin/batchIds.ts`（纯工具，不导出 Router），与 `routes/pagination.ts` 同类。
- 前端 `DataTable` 只提供「键集合的增删」，选择态是否跨页保留由调用方决定——本仓库四个页面一律在重新取数时清空。
