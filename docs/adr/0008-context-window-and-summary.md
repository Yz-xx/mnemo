# 上下文用「保留窗口 + 持久化滚动摘要」治理

agent-server 此前把整段会话历史原样喂给对话模型，长会话必然溢出模型窗口，且溢出后的行为没有约定、也没有观测。本文记录用「保留最近窗口 + 把更早对话压缩成可持久化的滚动摘要」治理上下文的整体取向，以及截断点语义、摘要合并策略、失败降级三处不可逆的定案。落库摘要这一层是阶段 3，阶段 1（确定性裁剪 + 观测）与阶段 2（单轮内工具结果治理）共用本文的 token 估算与保留窗口口径。

## 现状

- 历史由 [agent.ts](file:///d:/Files/common/porgram/my-monorepo/apps/agent-server/src/llm/agent.ts) 的 `toMessages()` 全量转换后注入，没有 token 计数、预算、超限策略与埋点；`config/env.ts` 里也没有任何窗口相关配置。
- `createAgent` 未挂 checkpointer，历史每轮都从 MySQL 全量重灌，因此摘要**必须落库**才可能跨轮生效——这排除了「靠框架中间件顺带持久化」的捷径。
- `messages` 表**已有自增列 `seq`**（`ORDER BY seq` 正在用于排序），但 `toStoredMessage()` 只映射了 `id` / `role` / `content` / 元数据，未把 `seq` 带出。
- 消息是 append-only：只有整会话删除（外键级联），`seq` 不会出现空洞。
- [Conversation](file:///d:/Files/common/porgram/my-monorepo/apps/agent-server/src/conversation/types.ts) 目前只有 `id` / `title` / 时间戳 / `messages`，没有任何摘要字段。

## 术语

- **保留窗口（retained window）**：每轮真正注入模型、逐字保留的最近若干轮对话，按 token 预算从新到旧整轮选取，保证 `user` / `assistant` 成对。
- **摘要（summary）**：被挤出保留窗口的更早对话经模型压缩后的一段文本，跨轮持久化。
- **截断点（`summary_upto_seq`）**：摘要已覆盖到的最后一条消息的 `seq`；未摘要段即 `seq > summary_upto_seq` 的消息。
- **触发**：本轮估算 token 超过窗口占用阈值，需要执行一次治理。

## 决策

1. **治理分三阶段落地**：阶段 1 确定性裁剪 + 观测，阶段 2 单轮内工具结果治理，阶段 3 持久化滚动摘要。各阶段可独立上线，本文锁阶段 3。
2. **摘要落库**：`conversations` 增加 `summary TEXT NULL` 与 `summary_upto_seq INT NULL` 两列，经 `ensureColumns` 的条件迁移补出，整段幂等。
3. **截断点用自增 `seq`**：给 `StoredMessage` 增补 `seq` 字段，未摘要段直接用 `WHERE seq > ?` 取。不用消息 UUID（无序、比较需额外查表），也不用「已摘要条数」（任何删除都会漂移）。
4. **摘要优先于丢弃**：触发时先把「保留窗口起点之前」的**全部未摘要段**交给模型做摘要；只有在摘要失败时才退化为丢弃最老。
5. **边界紧贴保留窗口，无 gap 无重叠**：摘要恰好覆盖到保留窗口起点之前的那一条，`summary_upto_seq` 推进到该条的 `seq`。于是下一轮的未摘要段 = 保留窗口 + 新增消息，既不漏段也不重复占位。
6. **增量合并**：合并输入是「旧摘要 + 新丢弃段」，输出新的单段摘要。摘要输出限长（提示词要求压缩到约定字数内），并把它计入 token 预算估算，防止误差随轮次累积。
7. **失败降级**：摘要调用失败时**不推进 `summary_upto_seq`**，本轮退化为阶段 1 的确定性丢弃，下轮重新尝试。摘要是「锦上添花」，任何时候都不阻断对话，也不污染截断点。
8. **写入保单调**：摘要回写用条件更新（`WHERE summary_upto_seq < ?`），保证截断点只增不减；并发请求下先落库的一次生效，后来者不覆盖，避免重复摘要或摘要与截断点不一致。
9. **注入形态**：摘要拼成一条 `SystemMessage` 插在历史消息之前，与现有附件预读（`appendAttachments`）同构，并在文本中声明「以下是此前对话的摘要」。
10. **摘要复用对话模型**：直接用 `createChatModel(config)` 的实例 `invoke` 一次，不走 agent、不带工具。不新增摘要模型配置；确有需要时再以「留空即复用」的形式追加。
11. **首条消息不做特殊保护**：不把会话首条提问钉在窗口内，一并交给摘要覆盖。

## Considered Options

- **用 LangChain 官方 `summarizationMiddleware` / `contextEditingMiddleware`**：本仓无 checkpointer，中间件状态不跨轮持久，摘要会每轮重算；且行为偏黑盒，与本仓「服务端能确定摆好的就别交给模型决策」的取向相抵。否决，改用自研的确定性组装。
- **只做确定性裁剪、不落库摘要**：实现最简，但被丢弃的远历史信息不可恢复。降级为失败兜底，不作主路径。
- **每次触发都对全历史重摘要**：质量最好，但成本随会话长度线性增长。否决，改用增量合并。
- **保留窗口与摘要允许重叠一段作缓冲**：更安全，但重复占位，且摘要内容会随轮次反复出现。否决，改紧贴衔接。
- **会话级锁串行化摘要写入**：最稳，但为低概率并发引入锁的复杂度。否决，改用条件更新。
- **截断点用消息 id 或条数**：分别有「无序」与「易漂移」的缺陷。否决。

## Consequences

- **实体类型变更外溢**：`StoredMessage` 增加 `seq` 后，测试夹具必须同步补齐（见 `.trae/rules/backend-design.md` 第 9 章）；`__vitest__` 有独立的 `tsconfig.json`，需一并核对。
- **加列不可逆**：`conversations` 的两列一经上线即随存量数据存在，迁移前须备份；`ensureColumns` 必须幂等，中断后下次启动可自愈。
- **多一次模型推理**：摘要触发会引入一次额外的模型调用（延迟与成本），由窗口占用阈值比例控制触发频率，并以埋点验证。
- **小模型摘要质量待实测**：`qwen2.5:7b` 的压缩质量需真实会话验证；摘要限长是防误差累积的第一道约束。
- **口径必须统一**：阶段 1 / 2 / 3 共用同一套 token 估算与保留窗口选择，「触发阈值」只应有一处定义，不得各阶段各写一份。
- **配置同步**：本方案新增的配置项需同步 `AppConfig` → `loadConfig()` → `.env.development` / `.env.production` → `apps/agent-server/README.md` 配置表。

## 待办（实施时）

- 阶段 1：`llm/context/` 纯函数（token 估算、保留窗口选择）+ 把上下文组装提成显式接缝 + 观测埋点。
- 阶段 2：检索按文档去重 + 每轮检索/读取总量预算。
- 阶段 3：`conversations` 加列、摘要生成与增量合并、失败降级、条件更新回写，以及对应单测。
