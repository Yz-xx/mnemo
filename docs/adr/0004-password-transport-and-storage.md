# 口令走应用层公钥加密传输，并以不可逆哈希存储

登录接口原先在请求体里直传 `{ username, password }` 明文，库中密码则是**硬编码密钥的定值 DES**。常识默认是「传输安全交给 HTTPS，存储安全交给哈希」，本文记录这里**在应用层多做一层**、以及为什么把 DES 一并换掉。

## 现状

- 三处发送点（管理网站登录、管理端新建用户、桌面端登录/注册）都是 `JSON.stringify({ username, password })`，服务端是纯 HTTP（`app.listen`）。
- 存储侧 `users.password` 存的是 `desEncrypt(password)`：**可逆**、**ECB 定值**、**密钥写在源码里**（`@repo/shared/crypto`）。库一旦泄露即全量口令泄露，且同一口令在所有库里密文相同。

## 决策

1. **传输**：新增 `GET /api/auth/public-key` 下发 RSA 公钥（JWK，只含 `kty`/`n`/`e`）。客户端用 WebCrypto 以 `RSA-OAEP` + `SHA-256` 加密口令字段，Base64 提交；服务端持私钥解密。**解不开即按参数非法返回 400，绝不回落到明文比对**——否则「传的是密文」这个前提形同虚设。
   - 密钥对在进程启动时生成，**不落盘、不进配置**，随重启轮换。客户端每次登录前重新取公钥，因此轮换不需要任何失效处理；也避免私钥被写进配置文件或镜像层——那些位置通常没有口令保护。
2. **存储**：改为 `scrypt` + 随机盐，格式 `scrypt$<盐hex>$<散列hex>`。旧数据沿用定值 DES 可校验通过，并借登录时手里已有的明文**惰性升级**为哈希，存量账号无需重置密码。

## Considered Options

- **只靠 HTTPS/TLS**：这是正解，也是完整的方案；但部署侧当前并未统一启用 TLS，代码层看不到任何防护，且它**不改善** DES 可逆存储这一更严重的相邻问题。故本方案定位是纵深防御，不替代 TLS。
- **挑战-响应（SRP / PAKE）**：不传输任何口令等价物，抗中间人最强；但需要引入算法实现、两端协议与状态改造，收益与当前威胁模型不匹配，暂不取。
- **保留 DES，只换密钥或改配置化**：否决。可逆存储本身不成立，换密钥只提高攻击者门槛，不改变「库泄露即口令泄露」。
- **口令先在前端哈希再传**：否决。前端哈希结果会变成等效口令，重放即可登录；且哈希值可被离线爆破。

## Consequences

- **必须与 HTTPS 配合**。明文 HTTP 下公钥本身可被中间人替换，应用层加密因此只挡得住被动嗅探与代理/日志留存，不是完整防护。这一点写在 `apps/admin-web` 与 `apps/agent-server` 的 README 里，避免被当成 TLS 的替代品。
- **WebCrypto 需要安全上下文**（HTTPS 或 localhost）。远程明文 HTTP 访问时 `crypto.subtle` 不存在，客户端直接报错提示改用 HTTPS，**不回落成明文发送**。
- **公钥不得缓存**：服务端密钥对随重启轮换，`encryptPassword` 每次调用都重新取。
- **迁移是惰性的**：只有再次登录过的账号才会换成哈希，长期不登录的账号仍是 DES 密文；`verifyPassword` 的前缀判断成为两代兼容的唯一接缝，等存量账号迁完才能删除 DES 依赖。
- 两端契约由 `apps/agent-server/src/__vitest__/authRoute.test.ts` 钉住：用真实 fetch + WebCrypto 走完整链路，并断言明文一律被拒。
