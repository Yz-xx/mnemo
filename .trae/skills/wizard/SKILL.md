# 向导

一个**向导（wizard）**是一个 bash 脚本，它一步步引导人类走完一段手动流程，这段流程手工做起来很烦，每次向 AI 重新解释也很烦。它会打开每个 URL，明确指出要点什么、复制什么，捕获各个值，把它们写到该去的地方（`.env`、GitHub 密钥），在每个阶段确认，并显示还剩多少个阶段。它可能会配置第三方服务、执行一次性的迁移，或把项目从一种状态移到另一种状态。

令人愉悦的 UX 已经由 [template.sh](template.sh) 解决：逐阶段进度、确认关口、跨平台打开 URL（包括 WSL）、隐藏式密钥输入、幂等的 `.env` 插入更新、`gh secret`／`gh variable` 写入，以及结尾总结。**你的工作只是界定这段流程的范围并编写它的各个阶段。**`STAGES` 标记之上的库在每个向导里都完全相同；这种一致性就是重点：绝不要手工编辑它。

向导默认是一次性的：为一次运行而构建，保存到一个临时位置或 `scripts/` 路径，任务完成后删除。只有当用户希望有一条可重复、应当长期留在仓库里的 setup 路径时才提交它。

## 流程

### 1. 界定流程范围

梳理出人类必须采取的每一个手动步骤，以及沿途被捕获的每一个值。先读仓库，不要上来就问：

- 对于 setup：`.env`、`.env.example`、`.env.*`、`README`、`docker-compose*`、框架配置，以及 `.github/workflows/*`（每一处 `secrets.*`／`vars.*` 引用都是向导必须产出的一个值）。
- 对于迁移或过渡：当前状态、目标状态，以及它们之间不可逆的操作。

然后向用户展示按顺序排列的阶段列表以及每个阶段产出的值，并确认：他们可以增加、删除或重新排序。

**完成标志：**每个阶段都按顺序命名，并且对每个被捕获的值，你都知道 (a) 人类从哪里获得它、(b) 它被写到哪里（`.env`、一个 GitHub 密钥、两者都要，或哪里都不写；有些阶段是纯粹的动作）、以及 (c) 它是密钥（隐藏式输入）还是公开的。

### 2. 勾画每个阶段的路径

对每个阶段，写出人类遵循的精确路径：打开哪个 URL、在那里做什么、某个值在哪里显示、它填充哪个变量。例如 “Dashboard → Developers → API keys → Reveal test key → copy”。在你并不真正了解当前 UI 或确切命令的地方，就如实说明，并询问用户或查阅文档：绝不要编造可能并不存在的步骤。

**完成标志：**每个阶段都能追溯为一份陌生人也能照做的具体指令。

### 3. 编写向导

把 `template.sh` 复制到目标路径。用每个步骤一个 `stage` 替换示例阶段，按依赖顺序排列。使用库里的辅助函数：`stage`、`say`/`step`、`open_url`、`ask`/`ask_secret`、`write_env`、`set_secret`/`set_var`、`pause`/`confirm`。把 `TOTAL_STAGES` 设为你所写阶段的数量。

守住模板设定的标准：在索要某个值之前先打开对应的 URL，任何密钥都用 `ask_secret`，每个需要持久化的值都用 `write_env`，只对 CI 真正需要的值用 `set_secret`，任何不可逆操作之前都 `confirm`。每个 `stage` 都会清屏，因此只有当前步骤可见：让一个阶段只做一件聚焦的任务，这样人类需要的内容不会被滚出屏幕。不要碰标记之上的库。

### 4. 验证并交接

- `bash -n <script>`；如果可用，运行 `shellcheck`。
- `chmod +x <script>`。
- 不要自己端到端运行它：它会打开浏览器并阻塞等待人类输入。改为静态地追踪它：第 1 步中的每个值都被捕获并落在第 1 步所说的位置，并且每个 `set_secret` 名称都与 CI 中某处 `secrets.*` 引用的名字完全一致。
- 告诉用户如何运行它。如果它是一条可重复的 setup 路径，就提交它并从 README 链接过去，这样下一个人会运行脚本，而不是去问 AI。
