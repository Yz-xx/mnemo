# 分诊

让项目议题追踪器上的议题沿着一套小型的分诊角色状态机流转。

如果本仓库把外部拉取请求（pull request）当作一种请求入口（见议题追踪器配置），那么分诊也要覆盖它们：**一个 PR 就是一份附带代码的议题**，使用相同的角色、相同的状态、相同的状态机，只是有几个差异点在下文以“针对 PR”标出。请按追踪器配置把裸写的 `#42` 解析为议题或 PR。

分诊期间向议题追踪器发布的每一条评论或议题，都**必须**以这段免责声明开头：

```
> *This was generated by AI during triage.*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md)：如何撰写经久耐用的 agent 简报
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)：`.out-of-scope/` 知识库如何运作

## 角色

两个**分类**角色：

- `bug`：某些东西坏了
- `enhancement`：新功能或改进

五个**状态**角色：

- `needs-triage`：维护者需要评估
- `needs-info`：等待报告者提供更多信息
- `ready-for-agent`：已完整规格化，可供 AFK agent 处理
- `ready-for-human`：需要人工实现
- `wontfix`：不会处理

对于 PR，相同的状态要对照所附带的代码来理解：`ready-for-agent` 表示已附带一份简报、应由 agent 对这份 diff 采取下一步；`ready-for-human` 表示已可供人工合并。

每个经过分诊的议题都应恰好带有一个分类角色和一个状态角色。如果状态角色冲突，请先标记出来并询问维护者，再做任何其他事情。

这些是规范的角色名。议题追踪器里实际使用的标签字符串可能不同。映射关系应当已经提供给你。如果没有，请告诉用户运行 `/setup-matt-pocock-skills`。

状态流转：未加标签的议题通常先进入 `needs-triage`；从那里它可以转到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。一旦报告者回复，`needs-info` 会回到 `needs-triage`。维护者随时可以覆盖；对于看起来不寻常的流转，先标记出来并询问，再继续。

## 调用

维护者调用 `/triage` 并用自然语言描述他们想要什么。解读请求并执行。示例：

- “给我看看任何需要注意的东西”
- “我们来看看 #42”（议题或 PR）
- “把 #42 移到 ready-for-agent”
- “有哪些已经就绪、可供 agent 接手的？”

## 展示需要注意的内容

查询议题追踪器，按从旧到新呈现三个桶：

1. **未加标签**：从未分诊过。
2. **`needs-triage`**：正在评估中。
3. **`needs-info` 且自上次分诊笔记以来报告者有活动**：需要重新评估。

当 PR 在范围内时，把外部 PR 也纳入这些桶，并给每行打上 `[PR]` 或 `[issue]` 标记。发现环节只呈现*外部* PR（议题追踪器配置定义了谁算作外部），因此协作者正在进行的 PR 不算分诊工作。这个过滤只用于发现环节；一个被明确点名的 PR 无论作者是谁都始终要被分诊。

展示数量以及每条一行摘要。让维护者来挑选。

## 分诊某个具体的议题或 PR

1. **收集上下文。**阅读完整的议题或 PR（正文、评论、标签、作者、日期；对于 PR，还要读 diff）。解析任何先前的分诊笔记，以免重复询问已解决的问题。使用项目的领域术语表探索代码库，尊重该领域的 ADR。对代码库执行两项检查：(a) **冗余**：按领域概念（而不只是请求的措辞）搜索所请求行为是否已有实现，并报告你查找过的位置。如果找到了，它就是已实现的 `wontfix`（第 5 步）。(b) **先前被拒**：阅读 `.out-of-scope/*.md`，浮现出任何与本次请求相似的内容。

2. **给出建议。**告诉维护者你建议的分类与状态及理由，再加上一份与请求相关的简要代码库总结（包括它是否已实现）。等待指示。

3. **核实主张。**在任何拷问之前，先检查该主张是否站得住。对于 bug，按报告者的步骤复现它。对于 PR，确认这份 diff 做了它所声称的事：检出它，运行相关测试或命令。报告结果：已确认（并给出代码路径）、失败，或细节不足（这是强烈的 `needs-info` 信号）。经过确认的核实能让 agent 简报强得多。

4. **拷问（如有需要）。**如果请求需要充实，两次调用 Skill 工具，分别传入 “grilling” 和 “domain-modeling”，一轮问题一轮问题地把它拷问成型，一边打磨领域术语，一边在决策落定时内联更新 `CONTEXT.md`／ADR。

5. **应用结果：**
   - `ready-for-agent`：发布一条 agent 简报评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`：结构与 agent 简报相同，但要注明为什么它不能委派（判断题、外部访问、设计决策、手动测试）。
   - `needs-info`：发布分诊笔记（模板见下）。
   - 对于 `wontfix`，关闭议题，评论内容取决于*为什么*：
     - **已实现**：该改动已存在于代码库中。指出它所在的位置；**不要**写入 `.out-of-scope/`（那个知识库是为*被拒*的请求准备的，不是为已构建的）。
     - **被拒（bug）**：给出礼貌的解释，然后关闭。
     - **被拒（enhancement）**：写入 `.out-of-scope/`，在评论中链接到它，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`：打上该角色。如果有部分进展，可选地加一条评论。

## 快速状态覆盖

如果维护者说“把 #42 移到 ready-for-agent”，相信他们并直接应用该角色。确认你即将做什么（角色变更、评论、关闭），然后执行。跳过拷问。如果要在没有拷问环节的情况下移到 `ready-for-agent`，询问他们是否想写一份 agent 简报。

## Needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

把拷问期间解决的一切都记录到“established so far”之下，这样工作不会丢失。问题必须具体且可操作，而不是“请提供更多信息”。

## 恢复先前的会话

如果议题或 PR 上存在先前的分诊笔记，请阅读它们，检查报告者是否已回答任何未决问题，并在继续之前呈现一幅更新的图景。不要重复询问已解决的问题。
