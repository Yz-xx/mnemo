# 询问 Matt

你记不住每一项技能，所以开口问。

**流程（flow）** 是穿过这些技能的一条路径。大多数路径沿着一条**主流程（main flow）**运行，另有两条**接入匝道（on-ramp）**汇入其中。其余技能要么独立存在，要么是运行在下层的词汇层。

## 主流程：想法 → 交付

大多数工作走的路线。你有一个想法，想把它做出来。

1. **`/grill-with-docs`** 通过访谈来打磨想法。只要你**在一个工作目录中工作**，就从这里开始：它是有状态的，会把学到的东西保留在 `CONTEXT.md` 和 ADR 里。（没有工作目录？改用 `/grill-me`，见"独立技能"一节。两者运行同一个 `/grilling` 原语；`grill-with-docs` 是那个会留下书面痕迹的，所以只要有一个可留下痕迹的仓库，它就是两者中更好的选择。）
2. **分支：你能否在对话中解决每一个问题？** 如果某个问题需要一个可运行的答案（状态、业务逻辑、必须亲眼见到的 UI），那就绕道去做一个原型，两个方向都靠 **`/handoff`** 搭桥（原型住在自己的目录里，而这正是 `/handoff` 的用途；见"阶段边界"）：
   - **`/handoff`** 出去，然后针对那个文件开一个全新的会话，
   - **`/prototype`** 用一次性代码回答该问题，
   - **`/handoff`** 把你学到的东西带回来，并从最初的想法讨论串里引用它。
3. **分支：这是一次跨会话的构建吗？**
   - **是** → 先 **`/to-spec`**（把讨论串转成规格），再用 **`/to-tickets`** 把它拆成曳光弹工单，每张都声明自己的**阻塞边（blocking edges）**。在本地跟踪器上，那就是 `.scratch/<feature>/issues/` 下每张工单一个文件，靠手工按阻塞优先的顺序推进；在真实跟踪器上，这些边会变成原生阻塞链接，于是任何阻塞项已完成的工单都能被领取：每张工单启动一次 **`/implement`**，每次之间 **`/clear`** 掉上下文。每张工单都是自包含的，所以上一张的上下文可以丢弃。
   - **否** → 就在这里、在同一个上下文窗口里 **`/implement`**。

   无论哪种方式，**`/implement`** 都通过内部驱动 **`/tdd`**（一次一个红-绿切片）来构建每个议题，然后以运行 **`/code-review`** 收尾，那是对差异做的双轴审查（Standards + Spec），之后再提交。当你只想以测试先行方式构建一个具体行为、而不需要完整规格时，就单独取用 **`/tdd`**；当你想针对某个固定基点审查一个分支或 PR 时，就单独取用 **`/code-review`**。

### 上下文卫生

让第 1 到 3 步待在**同一个不中断的上下文窗口**里（在 `/to-tickets` 之前不要压缩或清空），这样盘问、规格和工单都建立在同一份思考之上。随后每次 `/implement` 都重新开始，从工单出发。

其限制是 **[smart zone](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：模型仍能敏锐推理的那个窗口（当今最先进模型上约 150k tokens）。如果某个会话在 `/to-tickets` 之前就接近它，不要硬撑到退化；在最近的阶段边界处 `/compact` 然后继续（见"阶段边界"）。

## 接入匝道

一种会生成工作的起始处境，随后汇入主流程。

- **缺陷与请求堆积** → **`/triage`**。它让议题在分诊角色之间流转，产出 agent 可处理的议题，之后由 **`/implement`** 接手。

  分诊只针对**不是你创建的**议题：缺陷报告、外部涌入的功能请求，任何原始到来的东西。`/to-tickets` 产出的工单已经是 agent 可处理的，所以**不要分诊它们**。

- **有东西坏了** → **`/diagnosing-bugs`**。针对疑难的那一种：瞥一眼不肯现形的缺陷、间歇性的偶发故障、在两次已知良好状态之间悄悄混进来的回归。在拿到**紧凑的反馈回路**（一条已经会因*这个*缺陷而变红的命令）之前，它拒绝空谈理论，然后带着一个回归测试来修复。当真正的发现是"没有一个好的接缝能把缺陷锁死"时，它的复盘会交接给 **`/improve-codebase-architecture`**。

- **一场庞大、迷雾重重的工程：绿地项目或大型功能构建，大到一次会话装不下** → **`/wayfinder`**，这里认知负荷最高的流程。当从此处到目的地的路还看不见时，它在议题跟踪器上绘制一张由**决策工单（decision tickets）**组成的**共享地图**，一次解决一张，产出**决策，而非交付物**，直到迷雾被推开、道路清晰。**`/grill-with-docs`** 打磨的是你能在一次会话里握住的想法，而 wayfinder 是为了你握不住的那个想法，它更慢也更稠密，所以只留给这种情况，绝不用在范围明确的特性上。

  当地图变清晰时，**它负责交接，不负责构建**：在 **`/to-spec`** 处汇入主流程，由它把地图里相互链接的决策收敛成一份可构建的计划，然后照常 `/to-tickets` 和 `/implement`。把地图直接循环进 `/implement` 会跳过这次收敛，丢掉那些相互链接的细节，所以只有当这项工作最终证明真的不大时，才直奔 `/implement`。

## 代码库健康

不是功能工作，只是维护。

- **`/improve-codebase-architecture`** 在你有一点空闲时间、想让代码库保持良好的 agent 可操作状态时就运行。它浮现出**深化机会（deepening opportunities）**；挑中一个会*生成一个想法*，你可以带着它进入主流程的 `/grill-with-docs`。它是找出候选者的勘察；**`/codebase-design`**（下文）则是你设计所选那一个时的工作台。

## 下层的词汇

两份模型调用的参考，运行在其他技能*之下*，各自是其词汇的唯一真相来源。当问题出在**词**而不是流程上时，直接取用它们；或者让上面的技能把它们拉进来。

- **`/domain-modeling`**：打磨项目的*领域*语言：挑战一个含混的术语，化解一个超载的词（"account" 同时干三份差事），把难以逆转的决策记录成 ADR。它是 `/grill-with-docs` 为了保持 `CONTEXT.md` 是一份干净术语表而驱动的主动纪律。
- **`/codebase-design`** 是设计模块*形状*时用的深模块词汇（module、interface、depth、seam、adapter、leverage、locality）：在干净的接缝处用一个小接口藏住大量行为。`/tdd` 和 `/improve-codebase-architecture` 都说这门语言。

## 阶段边界

**阶段（phase）** 是会话内部的一块工作：盘问、实现、QA。在两个阶段的**边界**上，你有五个选项，而在它们之间做选择是整张地图里最模糊的决策：

- **继续（Continue）**：原地不动。零成本，零损失。
- **`/clear`**：清空窗口，适用于此处的一切对接下来的事都不重要时。
- **`/handoff`** 写出一个可携带的 markdown 文件。范围很窄：只适用于**新的 harness**、**新的目录**、**同事**，或在**阶段中途**分叉出一个支线任务。它买来的是可携带性。
- **Subagent**：把一个范围紧凑的任务送到它自己的窗口，然后拿回一份报告。
- **`/compact`** 压缩这份上下文，并用它播种一个新会话。这是**默认值**，位于决策树的底部，而不是第一顺位的取用项。

阅读 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 了解那棵有序的决策树：五个问题、每个分支背后的推理，以及为什么一手来源的代价让**继续**成为第一个被排除的选项。要在边界**处**做决定；阶段中途，要么继续，要么把剩下的拆给 subagent。

## 独立技能

完全在主流程之外。

- **`/grill-me`**：与 `/grill-with-docs` 同样无情的访谈，但**无状态**：它不在本地保存任何东西，也不构建 `CONTEXT.md`。当你**不在一个工作目录中工作**（打磨一份计划、一个设计、一篇文字，任何底下没有仓库的东西）时取用它。如果你在一个工作目录里，就用 `/grill-with-docs`：它运行同样的访谈并留下书面痕迹，所以它严格来说更好。
- **`/grilling`** 是访谈原语本身：轮次、前沿，事实是 agent 的活，决策是你的。`/grill-me` 和 `/grill-with-docs` 是两个命名的入口，而 `/triage`、`/wayfinder` 和 `/improve-codebase-architecture` 都在内部运行它。只有当你想要没有任何包装的访谈时，才直接取用它。
- **`/resolving-merge-conflicts`** 逐代码块（hunk）地处理进行中的 merge 或 rebase 冲突，依据**意图**（追溯到各方的一手来源）来解决，而不是挑几行，然后完成该操作。它从不运行 `--abort`。独立且在所有流程之外：当你已经身处冲突中途时取用它。
- **`/prototype`** 是一个小巧的一次性程序，用来回答一个设计问题：这个状态模型感觉对不对，或者这个 UI 应该长什么样。一次性是约束代码怎么写，而不是承诺要销毁它：答案会融进真实代码，而原型本身作为**一手来源**保留在 main 分出的 `prototype/<name>` 分支上，由实现议题指向它。它是主流程第 2 步里的那次绕道，但任何一次在纸上难以敲定的设计问题，都可以取用它。
- **`/research`**：把阅读的跑腿活交给一个**后台 agent**：它针对**一手来源**调研一个问题，然后在仓库里留下一份带引用的 Markdown 文件。它阅读的同时你继续工作。它产出的文件是可以*带入*主流程 `/grill-with-docs` 的素材，因为研究是喂养思考，而不是取代思考。
- **`/to-questionnaire`** 适用于阻塞你的东西不在你脑子里、也不在代码库里，而在**别人**那里的时候，它会给他们写一份问卷去填。它是 `/grill-me` 的逆操作：不去访谈你关于主题的想法，而是访谈你关于**发送**的想法（发给谁、你需要拿回什么），并把问题对准那道缺口。拿回来的东西是给 `/grill-with-docs` 或 `/to-spec` 的素材。
- **`/wizard`** 针对只有**人类**才能执行的步骤：准备基础设施、设置凭据或 CI 机密、点过一遍不熟悉的第三方仪表盘、运行一次性的迁移或切换。它生成一个交互式 bash 脚本，打开每个 URL、捕获每个值，并写入 `.env` 和 GitHub secrets，于是这套流程不再需要你每次向 agent 重新解释。它是模型调用的，所以 agent 一撞上只有你能通过的墙就会取用它。如果 agent 自己就能做，它就该自己做；这个技能用于人类确实在环中的场合。
- **`/wait-what`** 是针对一条没落地的消息的纠正手段。在对话中途、在任何其他技能内部使用它，agent 会用你缺的那点上下文、用大白话、并使用 `CONTEXT.md` 的词汇，把它刚说过的话重新讲一遍。它是事后补救；`/grill-with-docs` 是事前的解药，因为早早约定一门共同语言，才是让术语黑话根本不再到来的原因。
- **`/teach`**：跨多个会话学习一个概念，把当前目录当作有状态的工作区。
- **`/writing-for-agents`** 是撰写 agent 消费的文档时的参考：技能、AGENTS.md、被指向的文档。
