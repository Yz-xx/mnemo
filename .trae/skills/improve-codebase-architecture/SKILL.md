# 改进代码库架构

暴露架构上的摩擦点，并提出**深化机会（deepening opportunities）**：把浅模块（shallow module）改造成深模块（deep module）的重构。目标是可测试性与 AI 可导航性。

此命令以项目的领域模型为_依据_，并建立在共享的设计词汇之上：

- 调用 Skill 工具并传入 "codebase-design" 获取架构词汇（**模块（module）**、**接口（interface）**、**深度（depth）**、**接缝（seam）**、**适配器（adapter）**、**杠杆（leverage）**、**局部性（locality）**）及其原则（删除测试、"接口即测试面"、"一个适配器 = 假设的接缝，两个 = 真实的接缝"）。在每条建议中都要准确使用这些术语，不要滑向 "component"、"service"、"API" 或 "boundary"。
- `CONTEXT.md` 中的领域语言为好接缝命名；`docs/adr/` 中的 ADR 记录了此命令不应重新翻案的决策。

## 流程

### 1. 探索

**扫描之前先划定范围：YAGNI。** 深化模块的价值在于让未来对它的改动更容易，所以要把额外的权重放在代码库近期发生过变化的部分。在看之前先决定*看哪里*：

- 如果用户指明了方向（某个模块、某个子系统、某个痛点），就照它来，跳过下面的推断。
- 否则，回溯相当长一段提交历史（`git log --oneline`）来找出代码库的热点，即那些反复出现的文件和区域，让这些路径优先吸引你的注意力。如果改动零星分散、没有明确热点，就扩大搜索范围。

先阅读项目的领域词汇表（`CONTEXT.md`）以及你所触及区域的任何 ADR。

然后派生一个子代理（sub-agent）来遍历代码库。不要遵循刻板的启发式规则；有机地探索，并记录你在哪里感受到摩擦：

- 哪里为了理解一个概念需要在许多小模块之间来回跳转？
- 哪里模块**浅**，其接口几乎和实现一样复杂？
- 哪里纯粹为了可测试性抽出了纯函数，但真正的缺陷却藏在它们的调用方式里（缺乏**局部性**）？
- 哪里紧耦合的模块跨越了它们的接缝发生泄漏？
- 代码库的哪些部分未被测试，或者难以通过其当前接口进行测试？

对你怀疑为浅的东西应用**删除测试**：删除它会集中复杂性，还是只是把它挪个地方？"是的，会集中"正是你要的信号。

### 2. 以 HTML 报告呈现候选方案

把一个自包含的 HTML 文件写入操作系统临时目录，这样就不会有任何东西落到仓库里。从 `$TMPDIR` 解析临时目录，回退到 `/tmp`（Windows 上为 `%TEMP%`），并写入 `<tmpdir>/architecture-review-<timestamp>.html`，让每次运行都得到一个全新的文件。为用户打开它（Linux 上 `xdg-open <path>`，macOS 上 `open <path>`，Windows 上 `start <path>`），并告诉他们绝对路径。

报告通过 CDN 使用 **Tailwind** 来做布局与样式，通过 CDN 使用 **Mermaid** 来绘制那些用图形/流程/时序能可靠传达结构的图示。把 Mermaid 与手工打造的 CSS/SVG 视觉元素混用：当关系呈图形状（调用图、依赖、时序）时用 Mermaid，当你想要更具编辑感的东西（体量图、剖面图、折叠动画）时用手工搭建的 div/SVG。每个候选方案都要有**前后对比可视化（before/after visualisation）**。要有视觉感。

为每个候选方案渲染一张卡片，包含：

- **文件**：涉及哪些文件/模块
- **问题**：当前架构为何造成摩擦
- **解决方案**：用平实语言描述会改变什么
- **收益**：从局部性与杠杆的角度解释，以及测试会如何改善
- **前后对比图**：并排、自定义绘制，展示浅以及深化
- **推荐强度**：`Strong`、`Worth exploring`、`Speculative` 三者之一，渲染为徽章

报告以**首推建议（Top recommendation）**部分收尾：你会先处理哪个候选方案，以及为什么。

**领域用 CONTEXT.md 的词汇，架构用 `/codebase-design` 的词汇。** 如果 `CONTEXT.md` 定义了 "Order"，就说 "Order intake 模块"，而不是 "FooBarHandler"，也不是 "Order service"。

**ADR 冲突**：如果某个候选方案与既有 ADR 相矛盾，只有当摩擦真实到足以值得重新审视该 ADR 时才呈现它。在卡片中清楚标注（例如一个警告提示框：_"与 ADR-0007 矛盾，但值得重新打开，因为…"_）。不要列出 ADR 所禁止的每一项理论上的重构。

完整的 HTML 骨架、图示范式与样式指引见 [HTML-REPORT.md](HTML-REPORT.md)。

此时还不要提出接口。文件写完之后，问用户："你想探索其中哪一个？"

### 3. 追问推演循环（Grilling loop）

用户选定一个候选方案后，调用 Skill 工具并传入 "grilling"，与他们一起走决策树：约束、依赖、深化后模块的形态、接缝背后是什么、哪些测试能存活。

随着决策逐渐成形，副作用会就地发生；调用 Skill 工具并传入 "domain-modeling"，在过程中让领域模型保持最新：

- **要用一个不在 `CONTEXT.md` 中的概念给深化后的模块命名？** 把这个术语加入 `CONTEXT.md`。如果该文件不存在，就按需惰性创建。
- **在对话过程中把一个模糊的术语打磨清楚了？** 就地更新 `CONTEXT.md`。
- **用户以一个关键性理由否定了该候选方案？** 提议写一条 ADR，措辞为：_"要不要我把它记录为一条 ADR，好让未来的架构评审不再重复建议它？"_ 只有当这个理由确实是未来的探索者避免重复建议同一件事所需要的，才提议；跳过临时性的理由（"现在不值得做"）和不言自明的理由。
- **想为深化后的模块探索替代接口？** 调用 Skill 工具并传入 "codebase-design"，使用它的"设计两次（design-it-twice）"并行子代理模式。
