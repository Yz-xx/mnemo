# 原型

原型是**回答某个问题的用完即弃的代码**。问题决定形态。

## 选择分支

确定要回答的是哪个问题，借助用户的提示、周围的代码，或者在用户在的时候直接询问：

- **"这套逻辑 / 状态模型感觉对吗？"** → [LOGIC.md](LOGIC.md)。构建一个可分享的单一 HTML 文件（自由操作按钮加上分标签页的引导式走查），把状态机推过那些在纸面上难以推理的情形，并让非开发者也能操作。
- **"这应该长什么样？"** → [UI.md](UI.md)。在单一路由上生成若干个截然不同的 UI 变体，通过 URL 搜索参数和一个悬浮底栏来切换。

这两个分支产出的工件截然不同，所以选错会浪费整个原型。如果问题确实有歧义且联系不上用户，就默认选择与周围代码更匹配的那个分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部说明这一假设。

## 两者都适用的规则

1. **从第一天起就是用完即弃的，并清楚地标明这一点。** 把原型代码放在它实际会被使用的地方附近（紧挨着它为之做原型的模块或页面），让语境一目了然，但命名要让随便看一眼的人也能看出它是原型、不是生产代码。对于用完即弃的 UI 路由，遵守项目已经在用的任何路由约定；不要发明新的顶层结构。
2. **运行起来轻而易举。** UI 原型从项目任务运行器里的一条命令启动：`pnpm <name>`、`python <path>`、`bun <path>` 等等。逻辑演示是用户双击即可的单个 HTML 文件。无论哪种，启动它都不需要动脑。
3. **默认不做持久化。** 状态存在内存里。持久化是原型正在_检验_的东西，而不是它该依赖的东西。如果问题明确涉及数据库，就访问一个临时 DB 或一个命名清楚写着 "PROTOTYPE, wipe me" 的本地文件。
4. **跳过打磨。** 没有测试，除了让原型_可运行_所必需之外没有错误处理，没有抽象。要点是快速学到点什么。
5. **把状态亮出来。** 在每个操作之后（逻辑）或每次变体切换时（UI），打印或渲染完整的相关状态，让用户能看到发生了什么变化。
6. **完成后把它留存下来。** 把任何得到验证的决策融入真实代码，然后把原型本身作为一份**一手资料（primary source）**留存：把它提交到一个用完即弃的分支上、离开 main，并在实现议题上留一个指向该分支的上下文指针。也要把答案留存下来（结论以及它所了结的问题），放在议题或某次提交里。main 分支只保留那个得到验证的决策。
