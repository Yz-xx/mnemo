# 逻辑原型

一个单一、自包含的 HTML 文件（一个**可分享的演示**），让任何人都能通过点击按钮来驱动一个状态模型。当问题关乎**业务逻辑、状态转换或数据形态**时使用它：这类东西在纸面上看起来合理，但只有把它推过真实情形后才感觉不对劲。

因为它是单个文件、无需安装任何东西，你可以把它交给非开发者（设计师、PM、领域专家），让他们亲自感受这个模型。所以它说的是他们的语言，而不是代码的语言。

## 什么时候这是对的形态

- "我不确定这个状态机是否能处理 X 然后 Y 的那种边界情形。"
- "这个数据模型真的能让我表示……的那种情形吗"
- "我想在动手写之前先摸清这个 API 应该长什么样。"
- 任何有人想**按按钮并看着状态发生变化**的场景。

如果问题是 "这应该长什么样"，那就是错误的分支。请用 [UI.md](UI.md)。

## 流程

### 1. 陈述问题

在写代码之前，写下你正在为之做原型的状态模型和问题。一段话，放在演示的顶部（在一个可见的引言里，而不只是一条注释）。一个回答错误问题的逻辑原型纯属浪费，所以把问题写明确，以便日后可以核对，无论用户此刻在看着还是离开（AFK）之后再回来看。

### 2. 把逻辑隔离在一个可移植的模块里

把真正的逻辑（回答问题的那个部分）放在单个 `<script>` 块里，写成一个小而纯粹的模块，日后可以被取出并放进真实的代码库。它周围的页面是用完即弃的；这个模块不是。

正确的形态取决于问题：

- **一个纯 reducer**：`(state, action) => state`。当操作是离散事件、状态是单一值时适用。
- **一个状态机**：显式的状态与转换。当 "此刻哪些操作才是合法的" 也是问题的一部分时适用。
- **一组作用于普通数据类型的纯函数**。当不存在隐含的当前状态、只有转换时适用。
- **一个拥有清晰方法面的类或模块**，当逻辑确实拥有持续的内部状态时。

挑选最贴合所提问题的形态，*而非*最容易接到页面上的形态。保持它的纯粹：没有 DOM，没有 `document`，没有伸进它内部的按钮处理器。页面调用它；没有任何东西反向流动。这正是让原型在其自身生命周期之后仍有用的原因：一旦问题被回答，得到验证的 reducer / 状态机 / 函数集会自行提升进真实模块。

### 3. 构建可分享的 HTML 文件

单个文件，纯 HTML/CSS/JS：没有框架，没有打包器，没有服务器，一切内联，这样双击即可打开，也能经受住到处发邮件转发。任何人都应该能通过打开它来运行它。

面向非开发者来写。每个标签都用**领域语言**，而非代码：按钮和状态读起来像业务，而不是 reducer。用平实的话解释正在发生什么。

用干净的层级从上到下布局：

1. **标题和一行说明**，讲清这个演示让你探索什么（第 1 步的问题）。
2. **当前状态**：完整的相关状态，渲染为一个可读的面板（带标签的字段，而不是原始的 JSON 转储），每次点击后重新渲染，让变化可见。在有助于非开发者跟上的地方，把刚刚改变的东西点明。
3. **自由操作按钮**：每个操作一个按钮，始终可用，这样任何人都能以任意顺序摆弄这个模型。每次点击派发其操作并重新渲染状态。
4. **引导式走查**：一组**场景**，每个标签页一个。每个标签页放一段对场景的简短平实描述（它设定的情境，以及要留意什么），其下方是为该场景排好序的**要按的按钮**。每一步都是一个真实的按钮：点击它就执行该操作并前进到下一步。启动一次走查会重置到一个已知的初始状态，这样场景每次运行都一样。

挑选能展示那些别扭情形的场景，也就是在纸面上难以推理的那些：顺遂路径（happy path）、一个棘手的边界情形、一次对某件本应非法之事的尝试。

让它美观但克制：干净的排版、大方的间距、一个强调色。没有动画，没有花招：没有任何与状态和按钮争抢注意力的东西。

### 4. 交付

把文件发给他们，或者替他们打开。他们有空时就会点着走查和自由操作；有意思的时刻是当他们说 "等等，这不应该可能" 或 "咦，我以为 X 会不一样"；那些是_想法_里的缺陷，而这正是全部要点。如果他们想要新的操作或新场景，就加上。原型是会演化的。

### 5. 留存答案与原型

一旦原型回答了它的问题，就留存答案，然后按 [SKILL](SKILL.md) 所描述的方式留存原型。逻辑特有的对应关系：得到验证的 reducer / 状态机 / 函数集提升进真实模块（决策，被吸收）；HTML 外壳随之进入那个把原型留作一手资料、用完即弃的分支，而由于它是单个自包含文件，在那里它依然能轻而易举地重新运行。

## 反模式

- **不要加测试。** 一个需要测试的原型就不再是原型了。
- **不要把它接到真实数据库上。** 用内存状态，除非问题明确关乎持久化。
- **不要做泛化。** 不要 "假如我们以后想支持 X 呢"。原型只回答一个问题。
- **不要模糊逻辑与页面之间的界限。** 如果那个纯模块引用了 DOM、`document` 或按钮处理器，它就不再是可提取的。让页面只是纯模块之上的一层薄壳。
- **不要伸手去拿框架、打包器或服务器。** 一个收件人双击即可的文件；一个 React 应用或开发服务器会毁掉 "可分享"。
- **不要把 HTML 外壳发布到生产环境。** 页面是为手动点击走查而优化的。它背后的逻辑模块才是值得保留的部分。
