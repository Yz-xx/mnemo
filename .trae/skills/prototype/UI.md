# UI 原型

在单一路由上生成**若干个截然不同的 UI 变体**，从悬浮底栏切换。用户在浏览器里在变体之间来回切换，选定一个（或者从每个里各偷一点），然后把其余的扔掉。

如果问题关乎逻辑/状态，而非某样东西长什么样，那就是错误的分支。请用 [LOGIC.md](LOGIC.md)。

## 什么时候这是对的形态

- "这个页面应该长什么样？"
- "我想在定下来之前先看看这个仪表盘的几个选项。"
- "给设置界面试试另一种布局。"
- 任何用户否则会在脑子里在三个模糊的模型稿之间纠结一整天的时刻。

## 两种子形态：强烈偏向子形态 A

当 UI 原型**紧贴着应用的其余部分**时，判断起来容易得多：真实的页眉、真实的侧边栏、真实的数据、真实的密度。孤零零的一个用完即弃路由是一片真空：每个变体单看都挺好。只要有看似合理的既有页面可以承载这些变体，就默认用子形态 A。只有当原型确实没有附近的落脚处时，才去用子形态 B。

### 子形态 A：对既有页面的调整（首选）

路由已经存在。变体**在同一个路由上**渲染，由一个 `?variant=` URL 搜索参数控制。既有的数据获取、参数和鉴权全部保留。只有渲染被替换。这是默认做法；除非有具体理由不这么做，否则就选它。

如果原型所做的事物还没有页面，但*天然会活在某个页面里*（仪表盘的一个新区域、设置界面的一张新卡片、既有流程里的一个新步骤），那它仍属于子形态 A。把变体挂载在宿主页面内部。

### 子形态 B：新页面（最后手段）

只有当被做原型的东西确实没有既有页面可以栖身时才用它（例如一个全新的顶层界面，或者一个无法合理嵌入任何地方的流程）。

按照项目已经在用的任何路由约定创建一个**用完即弃的路由**。不要发明新的顶层结构。给它命名得一眼能看出是原型（例如在路径或文件名里包含 `prototype` 一词）。同样的 `?variant=` 模式。

在决定采用子形态 B 之前，先做个合理性检查：真的没有任何既有页面可以嵌入它吗？一个空路由会掩盖一个填满内容的路由会暴露出来的设计问题。

在两种子形态下，悬浮底栏都相同。

## 流程

### 1. 陈述问题并选定 N

默认 **3 个变体**。超过 5 个就不再是截然不同，而开始变成噪音，所以上限就定在那里。

用一行写下计划，放在原型所在的位置或文件顶部的注释里：

> "设置页面的三个变体，通过 `?variant=` 切换，位于既有的 `/settings` 路由上。"

无论用户是否在场提出反对意见，这都行得通。

### 2. 生成截然不同的变体

起草每个变体。让每个都符合：

- 页面的用途及它能访问到的数据。
- 项目的组件库 / 样式系统（TailwindCSS、shadcn、MUI、纯 CSS，随便是哪个）。
- 一个清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须在**结构上不同**：不同的布局、不同的信息层级、不同的主要可供性（affordance），而不只是不同的颜色。三个稍作微调的卡片网格不是 UI 原型，那是壁纸。如果两份草稿出来太相似，用明确的 "不要用卡片网格" 指引重做其中一个。

### 3. 把它们接起来

在路由上创建一个单一的切换器组件：

```tsx
// pseudo-code, adapt to the project's framework
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A', 'B', 'C']} current={variant} />
  </>
);
```

对于子形态 A（既有页面）：把所有既有的数据获取保留在切换器之上；每个变体只改变被渲染的子树。

对于子形态 B（新页面）：`/prototype/<name>` 下那个用完即弃的路由挂载同一个切换器。

### 4. 构建悬浮切换器

屏幕底部中央一条小的固定定位栏，包含三个部分：

- **左箭头**：切换到上一个变体（循环回绕）。
- **变体标签**：显示当前变体的键，如果变体导出了名字，也显示那个名字。例如 `B (Sidebar layout)`。
- **右箭头**：向前循环（回绕）。

行为：

- 点击箭头会更新 URL 搜索参数（使用框架的路由器，例如 Next 上的 `router.replace`、React Router 上的 `navigate` 等等），这样变体就可分享且刷新后稳定。
- 键盘：`←` 和 `→` 方向键也可循环切换。当 `<input>`、`<textarea>` 或 `[contenteditable]` 获得焦点时，不要拦截方向键。
- 在视觉上与页面区分开（例如高对比度的药丸形控件、微妙的阴影），这样它显然不属于被评估的设计。
- 在生产构建中隐藏：以 `process.env.NODE_ENV !== 'production'` 或等价检查为门槛，这样一个误合并的原型不会把这根栏发布给用户。

把切换器放在一个单一的共享组件里，让两种子形态都能复用它。把它放在项目里共享 UI 所处的位置。

### 5. 交付

把 URL（以及 `?variant=` 键）亮出来。用户有空时就会翻看。有意思的反馈通常是 **"我想要 B 的页眉配上 C 的侧边栏"**，那才是他们真正想要的设计。

### 6. 留存答案并清理

一旦某个变体胜出，就留存答案（哪个变体以及为什么），然后按 [SKILL](SKILL.md) 所描述的方式留存原型。把胜出者融入真实代码，把其余的移到用完即弃的分支上，而不是 main：

- **子形态 A**：把胜出者融入既有页面；从 main 中删掉落选的变体和切换器。
- **子形态 B**：把胜出的变体提升为一个真实路由；从 main 中删掉用完即弃的路由和切换器。

整套变体是一手资料，所以它落到用完即弃的分支上，而不是进垃圾桶，因为留在 main 分支里的变体组件和切换器会很快腐烂，并让下一个读者困惑。

## 反模式

- **只在颜色或文案上不同的变体。** 那是微调，不是原型。真正的变体在结构上有分歧。
- **在变体之间共享太多代码。** 共享的 `<Header>` 没问题；共享的 `<Layout>` 就砸了场子。每个变体都应该能自由地把布局扔掉。
- **把变体接到真实的变更操作上。** 只读的原型没问题。如果某个变体需要执行变更，就让它指向一个桩（stub）：问题是 "这应该长什么样"，而不是 "后端能工作吗"。
- **把原型直接提升到生产环境。** 变体代码是在原型的约束下写的（没有测试、最小的错误处理）。在把它融入时，要正式地重写它。
