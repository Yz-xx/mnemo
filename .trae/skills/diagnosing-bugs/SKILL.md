# 诊断缺陷

一套针对疑难缺陷的纪律。只有明确论证过才跳过阶段。

探索代码库时，阅读 `CONTEXT.md`（如果存在）以对相关模块建立清晰的心智模型，并查看你正在触及那一带的 ADR。

## 脱敏

本技能会要求你展示命令、输出和捕获的产物。**先给每个机密脱敏**：用 `<REDACTED>` 顶替。围绕环境变量构建回路，这样凭据留在环境里，而不是出现在你展示的东西里。捕获的产物会带有鉴权头：只引用携带信号的那些行。

如果脱敏后的输出不足以诊断该缺陷，就说出来并向用户求助。

## 阶段 1：构建反馈回路

**这就是这项技能的全部。** 其余都是机械操作。如果你能拿到该缺陷的**紧凑**通过/失败信号（一个会因*这个*缺陷而变红的信号），你就会找到病因；二分、假设检验和插桩都只是消耗它。如果你没有，盯着代码看再多也救不了你。

在这里投入不成比例的精力。**要激进。要有创意。拒绝放弃。**

### 构建回路的方式，大致按此顺序

1. **失败测试**，放在能触达该缺陷的任意接缝处：单元、集成、e2e。
2. **Curl / HTTP 脚本**，打向一个正在运行的开发服务器。
3. **CLI 调用**，带一份固定输入，把 stdout 与一份已知良好的快照做 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer），驱动 UI 并对 DOM/console/network 断言。
5. **重放一份捕获的 trace。** 把一次真实的网络请求 / payload / 事件日志存到磁盘，让它在隔离状态下重走代码路径。
6. **一次性 harness。** 起一个系统的最小子集（一个服务、mock 依赖），用一次函数调用就能走通缺陷所在的代码路径。
7. **属性 / 模糊测试回路。** 如果缺陷是"有时候输出错"，就跑 1000 个随机输入，找出失败模式。
8. **二分 harness。** 如果缺陷出现在两个已知状态（提交、数据集、版本）之间，自动化"在状态 X 启动、检查、重复"，这样你就能 `git bisect run` 它。
9. **差分回路。** 把同一个输入分别跑过旧版本与新版本（或两种配置），diff 输出。
10. **HITL bash 脚本。** 最后手段。如果必须由人来点击，就用 `scripts/hitl-loop.template.sh` 驱动*那个人*，好让回路仍然是结构化的。捕获到的输出会回传给你。

构建出正确的反馈回路，缺陷就已经修好 90% 了。

### 收紧回路

把回路当作一个产品。一旦你*有了*一个回路，就**收紧**它：

- 我能让它更快吗？（缓存准备工作、跳过无关的初始化、缩小测试范围。）
- 我能让信号更锐利吗？（对具体症状断言，而不是"没崩"。）
- 我能让它更确定吗？（钉住时间、给随机数发生器播种、隔离文件系统、冻结网络。）

一个 30 秒的偶发回路只是比没有回路略好一点；一个 2 秒的确定性回路才是紧凑的，是调试的超能力。

### 非确定性缺陷

目标不是一次干净的复现，而是**更高的复现率**。把触发循环 100 次、并行化、加压力、收窄时序窗口、注入 sleep。一个 50% 概率偶发的缺陷是可调试的；1% 不行，所以持续提高复现率，直到它可调试为止。

### 当你确实无法构建回路时

停下来并明确说出这一点。列出你试过的东西。向用户索要：(a) 能复现它的任何环境的访问权，(b) 一份脱敏的捕获产物（HAR 文件、日志转储、核心转储、带时间戳的录屏），或 (c) 添加临时生产插桩的许可。**不要**在没有回路的情况下推进到提出假设。

### 完成判据：一个会变红的紧凑回路

当回路**紧凑**且**能变红**时，阶段 1 就算完成：你能说出**一条命令**（一个脚本路径、一次测试调用、一条 curl），你**已经至少运行过它一次**（展示这次调用及其输出，已脱敏），并且它满足：

- [ ] **能变红**：它驱动真正的缺陷代码路径，并对**用户的确切症状**断言，所以它能在该缺陷上变红、在修复后变绿。不是"没报错地跑起来"；它必须能*抓住这个具体的缺陷*。
- [ ] **确定性**：每次运行的判决都一样（偶发缺陷：按上文所述，钉住一个高复现率）。
- [ ] **快**：以秒计，而不是以分钟计。
- [ ] **agent 可运行**：你能无人值守地运行它；人类只在通过 `scripts/hitl-loop.template.sh` 时才进入环中。

如果你发现在这条命令还不存在之前，自己就已经在读代码构建理论了，**停下来：径直跳到假设，正是本技能要防止的那种失败。** 没有能变红的命令，就没有阶段 2。

## 阶段 2：复现 + 最小化

运行回路。看着它随着缺陷出现而变红。

确认：

- [ ] 回路产生的是**用户**描述的那一失败模式，而不是恰好发生在附近的另一种失败。搞错缺陷 = 搞错修复。
- [ ] 该失败在多次运行中可复现（或者，对于非确定性缺陷，复现率足够高、可以据此调试）。
- [ ] 你已经捕获了确切的症状（错误消息、错误输出、缓慢的耗时），这样后续阶段才能验证修复确实解决了它。

### 最小化

一旦它变红，就把复现收缩到**仍然会变红的最小场景**。**一次一处**地砍掉输入、调用方、配置、数据和步骤，每砍一刀就重跑一次回路，只保留对失败有承重作用的那些。

为何要费这个劲：最小复现在阶段 3 缩小了假设空间（剩下可怀疑的活动部件更少），并在阶段 5 成为干净的回归测试。

完成于**剩下的每个元素都承重**之时：移除其中任何一个都会让回路变绿。

在你已经复现**并且**最小化之前，不要推进。

## 阶段 3：提出假设

在测试任何一个之前，先生成 **3 到 5 个排好序的假设**。只生成单个假设会锚定在第一个看起来合理的想法上。

每个假设都必须**可证伪**：陈述它所做出的预测。

> 格式："If <X> is the cause, then <changing Y> will make the bug disappear / <changing Z> will make it worse."（中文：如果 <X> 是原因，那么<改变 Y>会让缺陷消失 / <改变 Z>会让它更糟。）

如果你无法陈述那个预测，这个假设就是一种感觉：丢弃它，或把它磨得更锐利。

**在测试之前，把这份排好序的清单展示给用户。** 他们常常拥有能立刻重排顺序的领域知识（"我们刚对第 3 项部署了一个变更"），或者知道他们已经排除掉的假设。便宜的检查点，大大的省时。不要因此阻塞；如果用户 AFK，就按你自己的排序推进。

## 阶段 4：插桩

每个探针都必须对应阶段 3 中某个具体的预测。**一次只改变一个变量。**

工具偏好：

1. **调试器 / REPL 检视**，如果环境支持。一个断点胜过十条日志。
2. **有针对性的日志**，放在能区分假设的边界上。
3. 绝不要"把一切都记下来然后 grep"。

**给每条调试日志打标签**，用一个唯一前缀，例如 `[DEBUG-a4f2]`。最后的清理就变成一次 grep。没打标签的日志会活下来；打了标签的日志会死掉。

**性能分支。** 对于性能回归，日志通常是错的。改为：先建立基线测量（计时 harness、`performance.now()`、profiler、查询计划），然后二分。先测量，后修复。

## 阶段 5：修复 + 回归测试

**在修复之前**编写回归测试，但仅当存在一个**正确的接缝**时。

正确的接缝，是测试能在其中演练发生在调用点处的**真实缺陷模式**的接缝。如果唯一可用的接缝太浅（缺陷需要多个调用方时却只用单调用方测试，单元测试无法复现触发该缺陷的那条链），那里的回归测试会给出虚假的信心。

**如果不存在正确的接缝，这本身就是发现。** 记下它。代码库架构正在阻止该缺陷被锁死。为下一个阶段标记这一点。

如果存在正确的接缝：

1. 把最小化的复现变成该接缝处的一个失败测试。
2. 看着它失败。
3. 应用修复。
4. 看着它通过。
5. 针对原始（未最小化的）场景重跑阶段 1 的反馈回路。

## 阶段 6：清理

宣布完成之前必须做到：

- [ ] 原始复现不再复现（重跑阶段 1 的回路）
- [ ] 回归测试通过（或者，接缝缺失一事已被记录）
- [ ] 所有 `[DEBUG-...]` 插桩都被移除（`grep` 那个前缀）
- [ ] 一次性原型被删除（或移到一个清晰标记的调试位置）
- [ ] 被证明正确的那个假设在提交 / PR 消息里写明，好让下一个调试者学到东西
