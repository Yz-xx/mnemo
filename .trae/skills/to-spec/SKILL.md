本技能接收当前对话的上下文与对代码库的理解，并产出一份规格（spec）。不要访谈用户，只综合你已经掌握的内容。

议题追踪器（issue tracker）与分诊（triage）标签词汇表应当已经提供给你。如果没有，请告诉用户运行 `/setup-matt-pocock-skills`。

## 流程

1. 如果你还没有探索过仓库，先探索一遍，以了解代码库的当前状态。在整个规格中始终使用项目的领域术语表词汇，并尊重你所触及领域的任何 ADR。

2. 勾勒出你将要测试该功能的接缝（seam）。已有接缝应优先于新增接缝。尽量使用最高的接缝。如果确实需要新增接缝，请在你所能及的最高点提出它们。全代码库中的接缝越少越好，理想数量是一个。

与用户确认这些接缝符合他们的预期。

3. 用下面的模板撰写规格，然后发布到项目的议题追踪器。打上 `ready-for-agent` 分诊标签，无需再进行额外分诊。

<spec-template>

## 问题陈述

从用户视角描述用户正面临的问题。

## 解决方案

从用户视角描述问题的解决方案。

## 用户故事

一份很长、带编号的用户故事列表。每条用户故事应遵循如下格式：

1. As an <actor>, I want a <feature>, so that <benefit>（即：作为 <actor>，我想要 <feature>，以便 <benefit>）

<user-story-example>
1. As a mobile bank customer, I want to see balance on my accounts, so that I can make better informed decisions about my spending（作为一名移动银行客户，我希望查看我的账户余额，以便对支出做出更明智的决策）
</user-story-example>

这份用户故事列表应当极其详尽，覆盖该功能的方方面面。

## 实现决策

列出已做出的实现决策。可以包含：

- 将要构建或修改的模块
- 这些模块中将修改的接口
- 来自开发者的技术澄清
- 架构决策
- Schema 变更
- API 契约
- 特定的交互

不要包含具体的文件路径或代码片段。它们可能很快就会过时。

例外：如果某个原型产出的片段比文字更精确地编码了某项决策（状态机、reducer、schema、类型形状），请将其内联在相关决策中，并简要注明它来自某个原型。只保留富含决策的部分，不是可运行的演示，只需关键内容。

## 测试决策

列出已做出的测试决策。包含：

- 描述什么样的测试才算好测试（只测试外部行为，不测试实现细节）
- 将测试哪些模块
- 测试的先例（即代码库中类似类型的测试）

## 超出范围

描述本规格中超出范围（out of scope）的内容。

## 补充说明

关于该功能的任何补充说明。

</spec-template>
