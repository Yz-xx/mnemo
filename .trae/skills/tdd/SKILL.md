# 测试驱动开发

TDD 就是 red → green 循环。本技能是让这个循环产出值得保留的测试的参考资料：什么是好测试、测试放在哪里、反模式，以及循环的规则。每一节都适用于每一个循环：在循环之前和循环期间查阅它们，而不是在循环之后。

在探索代码库时，阅读 `CONTEXT.md`（如果存在），让测试名称和接口词汇与项目的领域语言相匹配，并尊重你所触及区域的 ADR。

## 什么是好测试

测试通过公共接口验证行为，而不是实现细节。代码可以完全改变；测试不应该。一个好测试读起来像一份规格："user can checkout with valid cart"（用户可以用有效购物车结账）准确告诉你存在什么能力，而且它能经受住重构，因为它不关心内部结构。

示例见 [tests.md](tests.md)，mock 指引见 [mocking.md](mocking.md)。

## 接缝（seam）：测试放在哪里

**接缝（seam）** 是你进行测试的公共边界：那个让你无需伸进内部就能观察行为的接口。测试住在接缝处，绝不针对内部。

**只在事先约定好的接缝处测试。** 在写任何测试之前，写下待测的接缝并与用户确认。不在未经确认的接缝处写测试。你不可能测试一切，所以事先约定接缝，是让测试精力落在关键路径和复杂逻辑上、而不是落在每个边界情形上的办法。

问："公共接口是什么，我们该测试哪些接缝？"

当那个接口的形态本身受到质疑时（模块有多深、接缝该在哪里、接口应该暴露什么），调用 Skill 工具并传入 "codebase-design" 获取词汇。它是模块、接口、深度、接缝、适配器、杠杆与局部性这些术语的共享来源，是一份供查阅的参考资料，而不是一个要运行的会话。

## 反模式

- **与实现耦合**：mock 内部协作者、测试私有方法，或通过旁路验证（查询数据库而不是使用接口）。破绽在于：当你重构但行为未变时，测试却坏了。
- **同义反复**：断言以代码同样的方式重新计算期望值（`expect(add(a, b)).toBe(a + b)`、以同样方式手工推导出的快照、一个断言等于自身的常量），所以它凭构造就通过，永远无法与代码产生分歧。期望值必须来自一个独立的事实来源：一个已知正确的字面量、一个做过的示例、规格。
- **水平切片**：先写完所有测试，再写所有实现。批量测试验证的是_想象中的_行为：你测试的是事物_的形态_，而不是面向用户的行为，测试对真实变化变得迟钝，而且你在理解实现之前就锁定了测试结构。改为以**垂直切片**工作：一个测试 → 一个实现 → 重复，每个测试都是一颗**曳光弹（tracer bullet）**，回应上一个循环教会你的东西。

## 循环的规则

- **先 red 后 green。** 先写失败的测试，然后只写刚好让它通过所需的代码。不要预判未来的测试，也不要添加投机性的功能。
- **一次一个切片。** 每个循环一个接缝、一个测试、一个最小实现。
- **重构不属于这个循环。** 它属于评审阶段（见 `code-review` 技能），而不属于 red → green 的实现循环。
