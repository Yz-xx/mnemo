# 生成工单

把一份计划、规格或对话拆解成一组**工单（ticket）**：曳光弹式的垂直切片，每个工单声明**阻塞**它的那些工单。

议题追踪器与分诊标签词汇表应当已经提供给你。如果没有，请告诉用户运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

基于对话上下文中已有的内容展开工作。如果用户以参数形式传入一个引用（规格路径、议题编号或 URL），请获取它并阅读其完整正文与评论。

### 2. 探索代码库（可选）

如果你还没有探索过代码库，请探索一番，以了解代码的当前状态。工单标题与描述应使用项目的领域术语表词汇，并尊重你所触及领域的 ADR。

寻找预重构（prefactor）代码的机会，让后续实现更轻松。“先让改动变简单，再做简单的改动。”

### 3. 起草垂直切片

把工作拆解成**曳光弹（tracer bullet）**工单。

<vertical-slice-rules>

- 每个切片都在每一层（schema、API、UI、测试）切出一条狭窄但**完整**的路径：是垂直的，而不是某一层的水平切片
- 一个完成的切片可以独立演示或验证
- 每个切片的大小应刚好能放进一个全新的上下文窗口
- 任何预重构都应最先完成

</vertical-slice-rules>

给每个工单标注它的**阻塞边（blocking edge）**：即必须在它开始之前完成的其他工单。没有阻塞者的工单可以立即开始。

**大范围重构是垂直切片的例外。**一次**大范围重构**指的是这样一次机械性改动（重命名一个列、给一个共享符号换类型），它的**爆炸半径（blast radius）**横跨整个代码库，因此一次编辑会同时打断成千上万个调用点，没有任何垂直切片能保持绿色。不要硬把它塞进曳光弹；把它编排成**扩展-收缩（expand–contract）**。先扩展：在旧形式旁边添加新形式，确保什么都不会坏。再迁移调用点，按爆炸半径分批（按包、按目录），每一批都是自己的工单，且被扩展工单阻塞；由于旧形式仍然存在，批与批之间 CI 保持绿色。最后收缩：在没有任何调用者残留后删除旧形式，用一个被所有迁移批次阻塞的工单来完成。当连各个批次都无法各自保持绿色时，保留这个序列，但让它们共享一个集成分支，并全部阻塞一个最终的集成并验证工单；只有在那个工单上才承诺绿色。

### 4. 向用户提问确认

以编号列表的形式呈现建议的拆解方案。对每个工单展示：

- **标题**：简短描述性名称
- **被谁阻塞**：哪些其他工单（如有）必须先完成
- **它交付什么**：该工单让哪些端到端行为变得可用

向用户提问：

- 粒度是否合适？（太粗还是太细）
- 阻塞边是否正确：每个工单是否只依赖真正约束它的那些工单？
- 是否有工单应当合并或进一步拆分？

反复迭代，直到用户批准该拆解方案。

### 5. 把工单发布到已配置的追踪器

发布已批准的工单。**如何**发布取决于 `/setup-matt-pocock-skills` 配置的追踪器；无论哪种方式工单本身都一样，只是阻塞边的形态不同：

- **本地文件** → 在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 下每个工单写一个文件，按依赖顺序从 `01` 开始编号（阻塞者在前）。每个文件的“被谁阻塞”列出它所依赖的编号／标题。使用下面的单工单文件模板：一个文件一个工单，绝不要写成单个合并文件。
- **真实议题追踪器（GitHub、Linear、…）** → 按依赖顺序（阻塞者在前）为每个工单发布一个议题，这样每个工单的阻塞边都能引用真实的标识符。如果平台有原生的阻塞／子议题关系就用它；否则把每个工单的“被谁阻塞”设为那些阻塞议题。除非另有指示，打上 `ready-for-agent` 分诊标签；按构造这些工单本就是 agent 可抓取的。

沿**前沿（frontier）**推进：即所有阻塞者都已完成的任何工单。对于纯线性链条，就是从顶到底。

不要关闭或修改任何父议题。
