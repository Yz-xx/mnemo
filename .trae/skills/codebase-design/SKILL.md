# 代码库设计

设计**深模块（deep module）**：在一个干净的接缝处，用一个小接口藏住大量行为，并通过该接口即可测试。凡是正在设计或重构代码的地方，都使用这门语言和这些原则。目标是给调用方带来杠杆（leverage）、给维护者带来局部性（locality）、给所有人带来可测试性。

## 术语表

严格使用这些术语：不要替换成"组件""服务""API"或"边界"。语言一致是全部的意义所在。

**Module（模块）**：任何同时拥有接口和实现的东西。刻意与规模无关：一个函数、类、包，或一个跨越多个层次的切片。_避免_：unit、component、service。

**Interface（接口）**：调用方为了正确使用该模块而必须知道的一切：类型签名，也包括不变量、顺序约束、错误模式、必需配置和性能特征。_避免_：API、signature（太窄，它们只指类型层面的表面）。

**Implementation（实现）**：模块内部的东西，它的代码体。与 **Adapter（适配器）** 相区别：一个东西可以是一个带大实现的小适配器（一个 Postgres 仓库），也可以是一个带小实现的大适配器（一个内存假实现）。当话题是接缝时用"adapter"；否则用"implementation"。

**Depth（深度）**：接口处的杠杆。调用方（或测试）每学会一单位接口，能施展的行为量。当一个模块用一个小接口藏住大量行为时，它是**深**的；当接口复杂到几乎与实现相当，它是**浅**的。

**Seam（接缝）** _(Michael Feathers)_：一个你可以改变行为而无需就地编辑的位置；是模块接口所在的*位置*。接缝放在哪里本身就是一项设计决策，与接缝后面放什么截然不同。_避免_：boundary（与 DDD 的限界上下文含义重叠）。

**Adapter（适配器）**：一个在某个接缝处满足某个接口的具体东西。描述的是*角色*（它填哪个槽），而不是实质（里面是什么）。

**Leverage（杠杆）**：调用方从深度中得到的。每学会一单位接口，换来更多能力。一份实现，回报遍及 N 个调用点和 M 个测试。

**Locality（局部性）**：维护者从深度中得到的。变更、缺陷、知识和验证集中在一处，而不是散布到各个调用方。修一次，处处都修好了。

## 深 vs 浅

**深模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│   Small Interface   │  ← Few methods, simple params
├─────────────────────┤
│                     │
│  Deep Implementation│  ← Complex logic hidden
│                     │
└─────────────────────┘
```

**浅模块** = 大接口 + 很少实现（避免）：

```
┌─────────────────────────────────┐
│       Large Interface           │  ← Many methods, complex params
├─────────────────────────────────┤
│  Thin Implementation            │  ← Just passes through
└─────────────────────────────────┘
```

设计一个接口时，问自己：

- 我能减少方法的数量吗？
- 我能简化参数吗？
- 我能把更多复杂度藏在里面吗？

## 原则

- **深度是接口的属性，不是实现的属性。** 一个深模块内部可以由小的、可 mock 的、可替换的部件组成；它们只是不属于接口的一部分。一个模块既可以有**内部接缝**（对其实现私有，供它自己的测试使用），也可以有位于其接口处的**外部接缝**。
- **删除测试（deletion test）。** 想象删除这个模块。如果复杂度随之消失，那它是个直通件。如果复杂度在 N 个调用方那里重新出现，那它是在挣自己的饭钱。
- **接口就是测试面。** 调用方和测试穿过同一个接缝。如果你想在接口*之外*做测试，这个模块的形状大概就不对。
- **一个适配器意味着一个假想的接缝。两个适配器才意味着一个真实的接缝。** 除非确实有东西跨接缝而变化，否则不要引入接缝。

## 为可测试性而设计

好的接口让测试变得自然：

1. **接受依赖，不要创建依赖。**

   ```typescript
   // Testable
   function processOrder(order, paymentGateway) {}

   // Hard to test
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不要制造副作用。**

   ```typescript
   // Testable
   function calculateDiscount(cart): Discount {}

   // Hard to test
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **小的表面积。** 方法更少 = 需要的测试更少。参数更少 = 测试搭建更简单。

## 关系

- 一个 **Module** 恰好拥有一个 **Interface**（它向调用方与测试呈现的表面）。
- **Depth** 是一个 **Module** 的属性，相对于它的 **Interface** 来衡量。
- 一个 **Seam** 是一个 **Module** 的 **Interface** 所在之处。
- 一个 **Adapter** 坐在一个 **Seam** 处，满足该 **Interface**。
- **Depth** 为调用方产生 **Leverage**，为维护者产生 **Locality**。

## 被否定的框架

- **把深度当作实现行数与接口行数的比值**（Ousterhout）：这会奖励往实现里灌水。我们改用"深度即杠杆"。
- **把"Interface"当作 TypeScript 的 `interface` 关键字或一个类的公开方法**：太窄了：此处的 interface 包含调用方必须知道的每一个事实。
- **"Boundary"**：与 DDD 的限界上下文含义重叠。请说 **seam** 或 **interface**。
