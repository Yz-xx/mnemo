# 深化

在给定依赖的情况下，如何安全地深化一簇浅模块。假定你已掌握 [SKILL.md](SKILL.md) 中的词汇：**module**、**interface**、**seam**、**adapter**。

## 依赖类别

在评估一个深化候选者时，给它的依赖分类。类别决定了深化后的模块如何跨越它的接缝被测试。

### 1. 进程内（In-process）

纯计算、内存状态、无 I/O。总是可深化的：合并这些模块，直接通过新接口测试。不需要适配器。

### 2. 本地可替代（Local-substitutable）

拥有本地测试替身的依赖（Postgres 用 PGLite、内存文件系统）。只要替身存在就可深化。深化后的模块在测试套件里用该替身运行来测试。接缝是内部的；模块的外部接口上没有端口。

### 3. 远程但自有（端口与适配器 / Ports & Adapters）

你自己跨越网络边界的服务（微服务、内部 API）。在接缝处定义一个**端口（port，接口）**。深模块拥有逻辑；传输层作为**适配器**注入。测试用内存适配器。生产用 HTTP/gRPC/队列适配器。

建议的措辞：_"Define a port at the seam, implement an HTTP adapter for production and an in-memory adapter for testing, so the logic sits in one deep module even though it's deployed across a network."_（中文：在接缝处定义一个端口，为生产实现一个 HTTP 适配器，为测试实现一个内存适配器，这样即便它跨网络部署，逻辑也坐在一个深模块里。）

### 4. 真正的外部（Mock）

你不掌控的第三方服务（Stripe、Twilio 等）。深化后的模块把外部依赖当作注入的端口；测试提供一个 mock 适配器。

## 接缝纪律

- **一个适配器意味着一个假想的接缝。两个适配器才意味着一个真实的接缝。** 除非至少有两个适配器说得通（通常是生产 + 测试），否则不要引入端口。单适配器的接缝只是额外的间接层。
- **内部接缝 vs 外部接缝。** 一个深模块既可以在接口处有外部接缝，也可以有内部接缝（对其实现私有，供它自己的测试使用）。不要仅仅因为测试要用，就把内部接缝暴露到接口上。

## 测试策略：替换，不要分层

- 一旦深化后模块接口处的测试存在，针对浅模块的旧单元测试就成了浪费；删掉它们。
- 在深化后模块的接口处编写新测试。**接口就是测试面**。
- 测试断言的是穿过接口的可观察结果，而不是内部状态。
- 测试应当能在内部重构中存活，因为它们描述的是行为，而不是实现。如果一个测试在实现变化时必须跟着改，那它就是在接口之外做测试。
